# Подключение счёта StandX

Пошаговая подготовка к работе бота: от кошелька до подтверждённого приватного
доступа. Все проверки делаются утилитой `standxctl`, ордера при этом не отправляются.

## 1. Кошелёк

Заводите **отдельный кошелёк под бота** и держите на нём только рабочую сумму.
Приватный ключ будет лежать на диске, поэтому его компрометация не должна
затрагивать основные средства.

Сеть — BSC (`chain: bsc` в конфигурации). Расчётный актив — DUSD.

## 2. Депозит

Депозит — чисто ончейн-операция, никакого запроса к API не требуется. DUSD
отправляется на адрес хранилища Highway:

| Сеть | Адрес хранилища |
| --- | --- |
| BSC | `0x11b660397382AE3A83c4Ad80e2F791189b39e433` |

> **Проверьте адрес самостоятельно перед отправкой.** Документация может отставать
> от фактического развёртывания контрактов. Минимальный депозит — 0.5 DUSD;
> отправьте сначала небольшую тестовую сумму и убедитесь, что она дошла.

## 3. Перевод в Perps Wallet

Это шаг, который легко пропустить. У StandX два кошелька, и депозит приходит
в **Cash Wallet**, тогда как торговля идёт с **Perps Wallet**. Пока средства
не переведены, `standxctl balance` покажет нули, а любой ордер будет отклонён
по нехватке маржи.

```bash
standxctl to-perps 1000     # Cash Wallet → Perps Wallet
standxctl to-spot  1000     # обратно, требуется перед выводом
```

## 4. Ключ

```bash
cp .env.example .env
chmod 600 .env
```

Впишите приватный ключ в `STANDX_WALLET_PK`. Файл `.env` исключён из репозитория.

Больше в `.env` ничего не кладётся. Все параметры бота — режим, инструменты,
аллокация, пределы риска — описаны в `config/config.yaml` и задаются только там.
Переменные `MMSTANDX_*` из прежней схемы не читаются; оставшуюся строку процесс
назовёт при старте, но действовать она не будет.

## 5. Проверка

```bash
make build

./bin/standxctl auth        # авторизация: подпись кошельком → JWT
./bin/standxctl balance     # средства Perps Wallet
./bin/standxctl symbols     # рынки и торговые спецификации
./bin/standxctl positions   # открытые позиции
./bin/standxctl orders      # висящие ордера
```

Успешный `auth` означает, что работает вся цепочка: подпись EIP-191 кошельком,
обмен на JWT и эфемерный ключ ed25519 для подписи тела запросов.

## Как устроен доступ

Схема двухключевая, и это существенно для безопасности.

**Ключ кошелька** доказывает личность ровно один раз — при выпуске токена.
Больше он ни в чём не участвует.

**Эфемерный ключ ed25519** создаётся на сессию и подписывает каждый торговый
запрос. Биржа связывает его с токеном на этапе `prepare-signin`, поэтому чужой
ключ не подпишет запрос под этим токеном.

Пара «токен + ключ сессии» сохраняется в `data/session.json` с правами `0600`.
Отсюда следует полезное свойство: **пока токен действует, переменная
`STANDX_WALLET_PK` не нужна вовсе** — бот поднимается из сохранённой сессии.
Ключ кошелька требуется только чтобы выпустить новый токен взамен истёкшего
(по умолчанию раз в сутки, настраивается `exchange.tokenTtl`).

Утечка файла сессии ограничена в последствиях: он истекает вместе с токеном
и **не позволяет вывести средства** — вывод требует ончейн-транзакции,
подписанной кошельком. Украсть можно торговую активность, но не деньги.

Файл с расширенными правами доступа считается скомпрометированным и молча
игнорируется — бот запросит вход заново вместо использования сомнительных
учётных данных.

## Что дальше

Проверенный доступ закрывает предусловие фазы 3 дорожной карты
([PLAN.md §11](../PLAN.md)) — дымового теста с реальными ордерами
минимального размера.

До этого бот работает в режиме `dry_run`, где путь отправки настоящего ордера
физически отсутствует в графе зависимостей: вместо биржевого клиента
подставляется заглушка. Переключение режима — осознанное действие
в `runtime.mode`.
